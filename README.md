# 🧩 객체 지향 설계 수준에 따른 PHP 코드의 유지보수성 비교


## 1. 🏗️ 비교 대상

### 01-concentrated

- 책임을 한 곳에 집중한 설계
- 클래스와 파일 수를 최소화
- 기능 흐름을 한 곳에서 확인하기 쉬움

### 02-overengineered

- 책임을 여러 객체로 과도하게 세분화한 설계
- 클래스와 파일 수가 크게 증가
- 개별 객체와 메서드의 책임은 작음

## 3. 🔍 분석


### Cyclomatic Complexity

02는 클래스와 메서드 수가 크게 증가하면서 전체 Cyclomatic Complexity도 `14 → 31`로 증가하였다.

다만 전체 복잡도는 메서드 수의 영향을 받기 때문에, 단순히 전체 수치만으로 개별 메서드의 복잡도를 비교하기는 어렵다.

- 01: `14 / 2 = 7.0`
- 02: `31 / 22 ≈ 1.41`

이를 통해 02는 전체 복잡도는 증가했지만, 복잡도가 여러 작은 메서드로 분산되어 있음을 확인할 수 있다.


### Cognitive Complexity

Cognitive Complexity는 예상과 반대되는 결과가 나왔다.

- 01: `16`
- 02: `9`

처음에는 여러 클래스를 이동하며 기능을 따라가야 하는 02의 인지 복잡도가 더 높을 것으로 예상하였다.

하지만 SonarQube의 Cognitive Complexity는 주로 조건문, 반복문, 중첩 구조 등 **코드 내부의 제어 흐름을 이해하기 어려운 정도**를 측정한다.

따라서 로직이 한 곳에 집중된 01은 제어 흐름이 복잡해져 Cognitive Complexity가 높게 측정되었고, 여러 객체로 로직을 분리한 02는 개별 메서드의 흐름이 단순해지면서 더 낮은 값이 측정된 것으로 보인다.

반면 다음과 같은 구조적 이해 비용은 Cognitive Complexity만으로 충분히 측정하기 어렵다.

- 기능을 이해하기 위해 이동해야 하는 파일 수
- 객체 간 의존 관계 추적
- 호출 흐름 탐색
- 전체 구조 파악 비용


## 4. 💡 중간 결론

### 01-concentrated

- 전체 구조가 단순함
- 기능 흐름을 한 곳에서 확인하기 쉬움
- 메서드 내부의 제어 흐름 복잡도가 높음


### 02-overengineered

- 개별 메서드의 제어 흐름이 단순함
- 클래스와 파일 수가 크게 증가함
- 전체 기능을 이해하기 위한 구조적 탐색 비용이 증가함


현재 결과를 통해 다음과 같이 정리할 수 있다.

> 지나친 책임 집중은 코드 내부의 복잡도를 높이고,  
> 지나친 객체 분리는 구조적 이해 비용을 높일 수 있다.

따라서 **객체를 많이 분리한다고 해서 유지보수성이 항상 좋아지는 것은 아니다.**
