# 🧩 객체 지향 설계 수준에 따른 PHP 코드의 유지보수성 비교

## 1. 프로젝트 개요

객체 지향 설계에서 **객체를 많이 분리할수록 유지보수성이 좋아지는가?** 라는 의문에서 시작한 프로젝트이다.

『오브젝트』에서 학습한 객체 지향 설계 원칙을 바탕으로 동일한 주문·결제 기능을 세 가지 구조로 구현하고, 정적 분석과 실제 요구사항 변경 실험을 통해 설계 수준에 따른 차이를 비교하였다.

**비교 대상**

| 설계 | 특징 |
|---|---|
| 01-concentrated | 하나의 클래스에 책임을 집중한 설계 |
| 02-overengineered | Interface, Factory 등을 활용해 책임을 과도하게 분리한 설계 |
| 03-flexible | 변경 가능성이 높은 책임을 중심으로 분리한 설계 |

- 언어: PHP
- 분석 도구: SonarQube, Git Diff
- 비교 기준: 코드 복잡도, 코드 규모, 변경 영향 범위, 이해 비용

## 2. 정적 분석 결과

### 2-1. 변경 요구사항 적용 전

| 지표 | 01 | 02 | 03 |
|---|---:|---:|---:|
| LOC | 85 | 272 | 204 |
| Files | 2 | 19 | 12 |
| Classes | 1 | 18 | 11 |
| Functions | 2 | 22 | 19 |
| Cyclomatic Complexity | 14 | 31 | 28 |
| Cognitive Complexity | 16 | 9 | 9 |
| Maintainability Rating | A | A | A |
| Issues | 3 | 19 | 13 |
| Duplication | 0% | 0% | 0% |

### 2-2. 분석 결과

**01-concentrated**
- 코드량과 클래스 수가 가장 적어 전체 구조가 단순하다.
- 하지만 여러 책임이 집중되어 Cognitive Complexity가 가장 높다.
- 새로운 정책을 추가할 때 기존 핵심 클래스를 수정해야 한다.

**02-overengineered**
- 책임 분리로 메서드 내부의 복잡도는 감소하였다.
- 반면 클래스와 파일 수가 크게 증가하여 객체 간 의존 관계와 호출 흐름을 파악하기 어려워졌다.
- 변경 가능성이 낮은 책임까지 추상화하여 구조적 복잡성이 증가하였다.

**03-flexible**
- 변경 가능성이 높은 할인, 배송, 결제, 저장 책임을 중심으로 분리하였다.
- 02와 동일한 Cognitive Complexity를 유지하면서 파일 수와 코드량을 줄였다.
- 불필요한 추상화를 줄여 유연성과 구조적 복잡성 사이의 균형을 고려하였다.

**정적 분석 결론**

책임을 분리하면 메서드 내부의 복잡도를 낮출 수 있지만, 지나친 객체 분리는 코드 규모와 구조적 이해 비용을 증가시킬 수 있다.

또한 SonarQube의 Cognitive Complexity는 주로 코드 내부의 제어 흐름 복잡도를 측정하므로, 객체 간 의존 관계를 이해하는 비용까지 나타내지는 못한다.

따라서 정적 분석만으로 유지보수성을 단정하기 어렵다.

## 3. 요구사항 변경 실험

세 설계에 동일한 변경 요구사항을 적용하여 실제 변경 범위를 비교하였다.

### 3-1. 변경 요구사항

1. 새로운 결제 방식(BANK) 추가
2. VIP 할인 정책 변경
3. SMS 알림 기능 추가

### 3-2. Git 변경 결과

| 지표 | 01 | 02 | 03 |
|---|---:|---:|---:|
| 변경 파일 수 (신규 포함) | 1 | 5 | 2 |
| 신규 파일 수 | 0 | 2 | 1 |
| 추가 라인 | +10 | +31 | +21 |
| 삭제 라인 | -1 | -1 | -1 |

**01-concentrated**
- `OrderService` 한 파일만 수정하였다.
- 변경량은 가장 적지만 새로운 요구사항이 기존 핵심 클래스에 계속 누적되는 구조이다.

**02-overengineered**
- 총 5개 파일에 변경이 발생하였다.
- 신규 구현뿐 아니라 Factory 등 기존 객체 생성 구조의 수정도 필요하였다.
- 추상화 계층이 많아 변경 시 확인하고 수정해야 하는 범위가 넓어졌다.

**03-flexible**
- 총 2개 파일에 변경이 발생하였다.
- 새로운 구현을 추가하고 객체 조립 구성을 변경하는 방식으로 대응하였다.
- 핵심 주문 처리 로직의 수정을 최소화하면서 기능을 확장하였다.

### 3-3. 요구사항 변경 후 SonarQube 분석

| 지표 | 01 | 02 | 03 |
|---|---:|---:|---:|
| LOC | 92 | 292 | 218 |
| Files | 2 | 21 | 13 |
| Classes | 1 | 20 | 12 |
| Functions | 2 | 24 | 20 |
| Cyclomatic Complexity | 17 | 34 | 30 |
| Cognitive Complexity | 20 | 10 | 10 |
| Issues | 5 | 21 | 14 |
| Maintainability Rating | A | A | A |

**주요 변화**

- 01: Cognitive Complexity `16 → 20` (+4)
- 02: Cognitive Complexity `9 → 10` (+1)
- 03: Cognitive Complexity `9 → 10` (+1)

01은 기존 클래스에 조건문과 분기가 추가되면서 내부 복잡도가 가장 크게 증가하였다.

반면 02와 03은 책임을 분리한 구조 덕분에 기존 메서드의 제어 흐름 복잡도 증가를 상대적으로 억제하였다.

다만 세 설계 모두 Maintainability Rating이 A로 측정되었으므로, 등급만으로 실제 변경 용이성의 차이를 판단하기는 어렵다.

## 4. 구조 이해 비용

기능을 이해하거나 변경하기 위해 개발자가 확인해야 하는 파일 수를 비교하였다.

| 지표 | 01 | 02 | 03 |
|---|---:|---:|---:|
| 평균 확인 파일 수 | 1.0개 | 3.1개 | 1.6개 |

- **01:** 한 파일에 기능이 집중되어 호출 흐름을 빠르게 파악할 수 있다.
- **02:** 여러 Interface, Factory, 구현 클래스를 따라가야 하므로 이해 비용이 가장 높다.
- **03:** 변경 가능한 정책을 분리하면서도 불필요한 계층을 줄여 탐색 범위를 축소하였다.

특히 02와 03은 Cognitive Complexity가 동일하지만, 기능을 이해하기 위해 확인해야 하는 파일 수에는 차이가 발생하였다.

이는 **정적 분석에서 측정하는 코드 내부 복잡도와 개발자가 체감하는 구조적 복잡도가 서로 다를 수 있음**을 보여준다.

## 5. 최종 결론

### Q1. 객체를 세분화할수록 유지보수성은 좋아지는가?

**반드시 그렇지는 않다.**

객체를 분리하면 개별 메서드의 복잡도를 줄일 수 있지만, 지나친 분리는 클래스와 의존 관계를 증가시켜 전체 구조를 이해하고 변경하는 비용을 높일 수 있다.

### Q2. 정적 분석 지표가 좋은 코드가 실제 요구사항 변경에도 유리한가?

**정적 분석 지표만으로 판단할 수 없다.**

01은 코드량과 전체 Cyclomatic Complexity가 가장 낮았지만, 변경 이후 Cognitive Complexity가 가장 크게 증가하였다.

반면 02와 03은 Cognitive Complexity가 동일했음에도 실제 변경 파일 수와 구조적 이해 비용에서 차이가 나타났다.

따라서 정적 분석은 잠재적인 코드 품질 문제를 식별하는 보조 지표로 활용하고, 실제 변경 영향 범위와 함께 평가해야 한다.

### Q3. 변경 용이성과 구조적 복잡성 사이에서 적절한 설계 수준은?

**변경 가능성이 높은 책임을 중심으로 필요한 만큼만 분리하는 설계이다.**

이번 실험에서 03-flexible은 02와 동일한 Cognitive Complexity를 유지하면서도 코드량과 클래스 수를 줄였으며, 실제 요구사항 변경 시 수정 범위와 구조적 탐색 비용도 상대적으로 작았다.

따라서 이번 실험 범위에서는 03-flexible이 **변경 용이성과 구조적 복잡성 사이에서 가장 균형 잡힌 설계**로 평가되었다.

다만 변경 요구사항의 종류와 시스템 규모에 따라 유리한 설계는 달라질 수 있다.

### 최종적으로 얻은 결론

> 좋은 객체 지향 설계는 객체를 최대한 많이 분리하는 것이 아니라, 변경 가능성이 높은 책임을 적절히 분리하여 변경의 영향을 최소화하면서도 전체 구조를 이해하기 쉽게 유지하는 것이다.

『오브젝트』에서 강조하는 책임 중심 설계와 의존성 관리의 중요성을 정적 분석과 실제 코드 변경 실험을 통해 확인할 수 있었다.
