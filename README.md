# 🧩 객체 지향 설계 수준에 따른 PHP 코드의 유지보수성 비교

## 🏗️ 1. 비교 대상

### 01-concentrated

- 책임을 한 곳에 집중한 설계
- 클래스와 파일 수를 최소화
- 기능 흐름을 한 곳에서 확인하기 쉬움
- 변경 가능한 정책과 핵심 로직이 하나의 클래스에 함께 존재

### 02-overengineered

- 책임을 여러 객체로 과도하게 세분화한 설계
- 단순한 책임까지 Interface, Factory 등의 별도 계층으로 분리
- 개별 객체와 메서드의 책임은 작지만 클래스와 파일 수가 크게 증가
- 기능을 이해하기 위해 여러 객체의 관계를 추적해야 함

### 03-flexible

『오브젝트』에서 학습한 내용을 바탕으로 **변경 가능성이 높은 책임을 중심으로 분리한 설계**

- 할인, 배송, 결제, 저장처럼 변경 가능성이 높은 부분을 별도 정책으로 분리
- `DiscountPolicy`, `ShippingPolicy`, `PaymentMethod`, `OrderRepository` 등의 추상화에 의존
- 구체 객체의 생성과 사용을 분리하여 `app.php`에서 객체를 조립
- Validation이나 단순한 `Order` 생성처럼 현재 변경 가능성이 낮은 부분은 불필요하게 추상화하지 않음
- 유연성과 구조적 복잡성 사이의 균형을 고려

## 🔍 3. 분석

### Cyclomatic Complexity

전체 Cyclomatic Complexity는 다음과 같이 측정되었다.

- 01: `14`
- 02: `31`
- 03: `28`

01은 클래스와 메서드 수가 적기 때문에 전체 Cyclomatic Complexity 역시 가장 낮다.

반면 02와 03은 책임을 여러 메서드와 객체로 분리하면서 전체 메서드 수가 증가하였기 때문에 전체 Cyclomatic Complexity 역시 증가하였다.

따라서 전체 Complexity만 비교하면 01이 가장 단순해 보이지만, 전체 복잡도는 메서드 수의 영향을 받기 때문에 **메서드당 평균 Complexity**도 함께 확인할 필요가 있다.

- 01: `14 / 2 = 7.0`
- 02: `31 / 22 ≈ 1.41`
- 03: `28 / 19 ≈ 1.47`

이를 통해 01은 소수의 메서드에 복잡도가 집중되어 있는 반면, 02와 03은 복잡도가 여러 작은 메서드로 분산되어 있음을 확인할 수 있다.

특히 03은 02보다 클래스와 메서드 수를 줄였음에도 메서드당 Complexity는 비슷한 수준을 유지하였다.


### Cognitive Complexity

Cognitive Complexity는 다음과 같다.

- 01: `16`
- 02: `9`
- 03: `9`

처음에는 여러 클래스를 이동하며 기능을 따라가야 하는 02의 인지 복잡도가 더 높을 것으로 예상하였다.

하지만 SonarQube의 Cognitive Complexity는 주로 조건문, 반복문, 중첩 구조 등 **메서드 내부의 제어 흐름을 이해하기 어려운 정도**를 측정한다.

따라서 로직이 한 곳에 집중된 01은 분기와 조건문의 수가 많아 Cognitive Complexity가 높게 측정되었다.

반면 02와 03은 할인, 배송, 결제 등의 책임을 별도 객체로 분리하면서 개별 메서드 내부의 제어 흐름이 단순해져 동일하게 `9`가 측정되었다.

다만 다음과 같은 비용은 Cognitive Complexity만으로는 충분히 측정하기 어렵다.

- 기능을 이해하기 위해 이동해야 하는 파일 수
- 객체 간 의존 관계 추적 비용
- 호출 흐름 탐색 비용
- 추상화 계층의 수
- 전체 구조를 파악하기 위한 비용

따라서 Cognitive Complexity가 동일한 02와 03이라도 구조적 복잡성까지 동일하다고 볼 수는 없다.


### 코드 규모

코드 규모는 세 설계의 차이를 가장 명확하게 보여준다.

| 항목 | 01 | 02 | 03 |
|---|---:|---:|---:|
| LOC | 85 | 272 | 204 |
| Files | 2 | 19 | 12 |
| Classes | 1 | 18 | 11 |

02는 책임을 세분화하면서 LOC가 01의 약 3배 이상 증가하였고, 클래스 수도 `1 → 18`로 크게 증가하였다.

03 역시 유연한 설계를 위해 여러 객체와 추상화를 도입했기 때문에 01보다 코드 규모가 증가하였다.

그러나 02와 비교하면:

- Files: `19 → 12`
- Classes: `18 → 11`
- LOC: `272 → 204`

로 감소하였다.

이는 03에서 모든 책임을 별도 객체로 분리하지 않고, **실제로 변경 가능성이 높은 할인, 배송, 결제, 저장 영역에만 추상화를 적용했기 때문**으로 볼 수 있다.


### Issues

SonarQube Issues는 다음과 같다.

- 01: `3`
- 02: `19`
- 03: `13`

01은 코드 자체가 매우 작기 때문에 Issue 수도 가장 적다.

02는 클래스와 코드량이 크게 증가하면서 Issue 역시 가장 많이 발생하였다.

03은 01보다는 많은 코드와 클래스를 가지고 있지만 02와 비교하면:

`19 → 13`

으로 감소하였다.

따라서 유연성을 위한 구조를 유지하면서도 과도한 객체 분리를 줄인 결과 전체 코드 규모와 함께 정적 분석 Issue도 감소한 것으로 볼 수 있다.

다만 Issue 개수는 코드량에 영향을 받으며 Issue의 종류와 심각도 역시 다르므로, 단순 개수만으로 설계 품질을 판단해서는 안 된다.


## 💡 4. 세 설계 비교

### 01-concentrated

**장점**

- 코드량과 클래스 수가 가장 적음
- 전체 기능 흐름을 한 파일에서 빠르게 확인 가능
- 구조를 이해하기 쉬움

**단점**

- 여러 책임이 하나의 클래스에 집중
- 조건문과 분기가 증가하여 메서드 내부 복잡도가 높음
- 할인, 배송, 결제 등의 정책 변경 시 동일한 핵심 클래스를 계속 수정해야 함


### 02-overengineered

**장점**

- 각 객체와 메서드의 책임이 작음
- 개별 메서드의 제어 흐름이 단순함
- 각 기능이 명확하게 분리됨

**단점**

- 단순한 책임까지 Interface, Factory 등으로 분리
- 클래스와 파일 수가 크게 증가
- 하나의 기능을 이해하기 위해 여러 파일과 객체 관계를 따라가야 함
- 실제 변경 가능성에 비해 지나치게 많은 추상화가 존재


### 03-flexible

**장점**

- 변경 가능성이 높은 할인, 배송, 결제, 저장 책임을 분리
- 추상화에 의존하여 구체 구현을 교체할 수 있음
- 객체 생성과 사용을 분리
- 02와 동일한 Cognitive Complexity `9`를 유지하면서 클래스와 코드량 감소
- 새로운 정책을 추가할 때 핵심 주문 로직의 수정 범위를 줄일 수 있는 구조

**단점**

- 01보다 클래스와 파일 수가 많음
- 인터페이스와 객체 간 협력을 이해해야 하므로 구조적 복잡성이 추가됨
- 단순한 요구사항만 존재한다면 01보다 불필요하게 복잡한 구조가 될 수도 있음


## 📚 5. 『오브젝트』 학습 내용의 적용

03-flexible에서는 다음 설계 원칙을 적용하였다.

### 책임을 분할의 중심축으로 사용

데이터가 아닌 객체가 수행해야 하는 책임을 기준으로 할인, 배송, 결제, 저장 기능을 분리하였다.

### 추상화 사용

`OrderService`가 구체적인 구현 클래스가 아니라 다음 추상화에 의존하도록 구성하였다.

- `DiscountPolicy`
- `ShippingPolicy`
- `PaymentMethod`
- `OrderRepository`

### 컴파일타임 의존성과 런타임 의존성 분리

컴파일타임에는:

`OrderService → DiscountPolicy`

와 같이 추상화에 의존하지만, 런타임에는:

`OrderService → RateDiscountPolicy`

와 같이 실제 구체 객체와 협력하도록 구성하였다.

### 생성과 사용의 분리

`OrderService` 내부에서 구체 객체를 직접 생성하지 않고 `app.php`에서 필요한 객체를 생성하여 주입하였다.

따라서 `OrderService`는 객체의 생성 방법보다 자신의 주문 처리 책임에 집중할 수 있다.

### 의존성 역전 원칙(DIP)

상위 수준의 주문 처리 로직이 `CardPayment`, `RateDiscountPolicy` 등의 구체 구현에 직접 의존하지 않고 추상화에 의존하도록 구성하였다.

### OCP

새로운 할인 정책이나 결제 방식을 추가할 때 기존 `OrderService`를 수정하기보다 새로운 구현 객체를 추가하거나 조립 구성을 변경하는 방식으로 확장할 수 있도록 하였다.

### 상속보다 합성

정책별 클래스를 상속 계층으로 조합하기보다 `OrderService`가 여러 정책 객체를 가지고 협력하도록 구성하였다.

이를 통해 클래스 관계를 컴파일타임에 고정하기보다 런타임에 필요한 객체를 조합할 수 있도록 하였다.

### 필요한 부분에만 유연성 적용

Validation, 단순한 `Order` 생성 등 현재 변경 가능성이 낮은 책임까지 Interface나 Factory로 분리하지 않았다.

이는 유연한 설계가 추가적인 추상화와 구조적 복잡성을 동반한다는 점을 고려한 것이다.


## 🎯 6. 정적 분석 단계 결론

정적 분석 결과만 보면 세 설계에는 각각 다른 특성이 나타났다.

`01-concentrated`는 코드 규모와 전체 Complexity가 가장 작지만, 소수의 메서드에 복잡도가 집중되어 Cognitive Complexity가 가장 높았다.

`02-overengineered`는 책임을 여러 객체에 분산하면서 메서드 내부의 Cognitive Complexity는 낮아졌지만, 클래스와 파일 수가 크게 증가하여 구조적 이해 비용이 증가하였다.

`03-flexible`은 Cognitive Complexity를 02와 동일한 `9`로 유지하면서도 LOC, Files, Classes, Issues 수를 02보다 줄였다.

이를 통해 현재 정적 분석 단계에서는 다음과 같은 특징을 확인할 수 있었다.

> **책임을 적절히 분리하면 메서드 내부의 복잡도를 낮출 수 있지만, 지나친 객체 분리는 코드와 구조 자체의 복잡성을 증가시킬 수 있다.**

또한 03은 모든 책임을 추상화하기보다 실제 변경 가능성이 높은 영역을 중심으로 추상화를 적용함으로써, 02보다 적은 구조적 비용으로 유연성을 확보하는 방향으로 설계하였다.

다만 **현재의 정적 분석 결과만으로 03의 유지보수성이 가장 높다고 단정할 수는 없다.**

유연한 설계의 장점은 실제 요구사항이 변경되었을 때 나타나기 때문이다.


## 🔄 7. 다음 단계

세 설계에 동일한 변경 요구사항을 적용하여 실제 변경 비용을 비교한다.

예를 들어 다음과 같은 요구사항을 적용한다.

- 새로운 회원 등급 및 할인 정책 추가
- 새로운 결제 방식 추가
- 배송 정책 변경

각 변경에 대해 다음 항목을 측정한다.

- 기존 수정 파일 수
- 신규 파일 수
- 변경 LOC
- 기존 코드 수정 범위
- Git Diff
- Cyclomatic Complexity 변화
- Cognitive Complexity 변화

이를 통해 단순히 현재 코드의 정적 품질뿐만 아니라,

> **요구사항 변경에 각 설계가 얼마나 적은 영향을 받는가**

를 비교하여 최종적으로 유지보수성과 설계 유연성을 평가한다.
